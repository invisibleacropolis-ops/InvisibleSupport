REFACTOR
The paradigm of software engineering is undergoing a fundamental shift with the introduction of autonomous Agent Engineers—Large Language Model (LLM) based systems capable of reading, reasoning about, and modifying source code. While human engineers can mentally navigate spaghetti code by relying on intuition and accumulated tribal knowledge, Agent Engineers operate under strict constraints defined by their context window and reasoning capabilities. The legacy monolithic index.html—a structure characterizing the early web, where structure (HTML), presentation (CSS), and behavior (JavaScript) are entangled in a single file—presents a "hostile environment" for these agents.
This report outlines a comprehensive master plan to refactor a monolithic support site into a modular, agent-optimized architecture. The objective is not merely code cleanliness but Context Engineering: restructuring the codebase to maximize the "signal-to-noise" ratio for LLMs.1 When an agent attempts to modify a feature within a 5,000-line monolith, it consumes thousands of tokens ingesting irrelevant code, increasing the probability of "lost-in-the-middle" errors, hallucinations, and context window overflow.2
To enable Agent Engineers to maintain and evolve this system effectively, we must transition from a horizontal, monolithic structure to a Vertical Slice Architecture (VSA). This approach organizes code by feature rather than technology, creating self-contained units of logic that fit neatly within an agent's operational context.4 By leveraging native browser standards—ES Modules (ESM) and Web Components—we eliminate the need for complex build tools that often obfuscate code for agents, ensuring the system remains "vanilla," performant, and enduring.6
This transformation rests on a critical mandate: the refactored system must preserve the exact UI and functions of the original. This requires a rigorous "Safety Net" strategy rooted in Visual Regression Testing (VRT) to detect sub-pixel deviations that functional tests might miss.8 The following sections detail the theoretical underpinnings, architectural patterns, and execution protocols necessary to achieve this metamorphosis.
2. Theoretical Framework: Context Economics and Architecture
Understanding why a monolith fails Agent Engineers requires an analysis of "Context Economics"—the cost and efficiency of information processing by LLMs.
2.1 The Monolith as a Contextual Liability
In a monolithic architecture, the entire application state is often global. Functions rely on variables declared thousands of lines away, and HTML elements are manipulated by scripts scattered throughout the document. For an agent to safely modify a single function (e.g., validateEmail), it ideally needs to "see" every part of the file that might interact with that function.
Token Saturation: A large index.html file can easily exceed 20,000 tokens. If an agent's efficient reasoning window is 32k or even 128k, a significant portion is wasted on irrelevant CSS or HTML markup for unrelated sections (e.g., the footer or sidebar) when the task is focused on the "Login" feature.1
Cognitive Load and Retrieval: LLMs perform best when relevant information is dense and contiguous. In a monolith, logical dependencies are spatially distant. The agent must effectively perform a "needle in a haystack" retrieval to find the definition of a variable used in an inline event handler, increasing the likelihood of reasoning errors.10
The "40% Rule": Empirical observations suggest that LLM performance degrades noticeably when the relevant context exceeds 40% of the available window. A monolithic file ensures that almost every task starts with a context load near or above this threshold, limiting the space available for reasoning, scratchpads, and generation.1
2.2 Vertical Slice Architecture (VSA) for Agents
The proposed solution is Vertical Slice Architecture. Unlike Layered Architecture (Horizontal), which groups code by technical role (Controllers, Models, Views), VSA groups code by Feature or Use Case.

2.3 The "Vanilla" Mandate: Avoiding Toolchain Obfuscation
While modern frameworks (React, Angular) encourage componentization, they introduce build steps (transpilation, bundling) that create a disparity between the source code the agent writes and the runtime code the browser executes. This "source map gap" complicates debugging for agents.
By utilizing Native Web Standards (ES Modules and Custom Elements), we ensure:
Code Transparency: The code the agent writes is the exact code the browser runs.
Long-Term Viability: Standards-based code does not suffer from "framework rot" or breaking changes in build tools.6
No-Build Simplicity: Agents can create, save, and test files immediately without waiting for complex webpack configurations or resolving dependency hell.12
3. Phase I: Establishing the Visual Verification Safety Net
Refactoring legacy code is inherently risky. The prompt specifies preserving "the exact same UI and functions." Subjective human review is insufficient and unscalable for verifying thousands of states after every agent modification. We must establish an automated Visual Regression Testing (VRT) protocol before any code is moved.8
3.1 VRT Methodology and Tool Selection
Visual Regression Testing involves capturing baseline screenshots of the application in its known-good state and comparing them against screenshots taken after code changes. Discrepancies are highlighted as "diffs."
Tool Selection: Playwright
Playwright is the optimal choice for this master plan due to its robust handling of modern web standards, cross-browser support (Chromium, Firefox, WebKit), and powerful auto-waiting mechanisms that reduce test flakiness.9 Its native toHaveScreenshot() assertion integrates deeply with the test runner, allowing Agent Engineers to execute tests and parse results programmatically.
3.2 Addressing Determinism and Flakiness
Legacy monoliths often contain non-deterministic elements (timestamps, random IDs, animations) that cause false positives in VRT. To create a stable baseline, the test environment must be strictly controlled.
Strategies for Stability:
Animation Freezing: Inject CSS to disable transitions and animations during testing.
JavaScript
await page.addStyleTag({ content: `
  *, *::before, *::after {
    animation-duration: 0s!important;
    transition-duration: 0s!important;
  }
`});


Data Mocking: Intercept network requests to provide static, deterministic JSON responses. This ensures that the "Latest Tickets" list always contains the exact same test data, preventing visual diffs caused by changing content.9
Dynamic Content Masking: Use Playwright's mask option to overlay solid color boxes on unavoidable dynamic elements (e.g., "Current Server Time" displays).8
Font Standardization: Web font loading can cause layout shifts. Tests should wait for document.fonts.ready before capturing snapshots.15
3.3 The Baseline Capture Protocol
The first task for the Agent Engineer is to crawl the existing index.html and generate a comprehensive suite of baseline images.
Protocol:
State Identification: Map all interactive states (e.g., Default View, Modal Open, Form Error State, Navigation Hover).
Test Generation: Write a Playwright spec file (visual.spec.js) that programmatically visits these states.
Baseline Commit: Run npx playwright test --update-snapshots to save the "Golden Master" images. These images represent the "Truth" of the legacy system.16
Example Agent Prompt for Baseline Creation:
"Analyze the DOM of index.html. Identify all interactive elements (buttons, inputs). Create a Playwright test file that clicks each interactive element, waits for the DOM to settle, and takes a named screenshot. Ensure you mask the element with ID #random-session-id."
4. Phase II: De-Spaghettification and Scope Remediation
The most significant barrier to modularization in legacy monoliths is the entanglement of scopes. Functions are defined globally; event handlers are inline in HTML; and state is implicitly stored in DOM attributes. Before we can extract "Slices," we must decouple these dependencies.
4.1 The Inline Event Handler Problem
Legacy HTML is rife with attributes like <button onclick="submitForm(this)">. This pattern is detrimental for three reasons:
Global Scope Dependency: The submitForm function must be on the window object, preventing us from moving it into an ES Module (which is module-scoped).18
Context Pollution: It mixes behavior with presentation, forcing the agent to read HTML to understand logic flows.19
Refactoring Blocker: You cannot safely rename or move the function without parsing the entire HTML string.
4.2 Automated Remediation with Codemods (AST Transformation)
Manually rewriting thousands of inline handlers is prone to error. We employ AST (Abstract Syntax Tree) transformation tools like jscodeshift to automate this process. An AST traversal allows us to surgically identify specific code patterns and rewrite them without affecting surrounding code.20
The Transformation Logic:
Parse HTML/JS: Identify elements with on[event] attributes.
Generate ID: If the element lacks an ID, generate a stable, semantic ID (e.g., js-autogen-btn-1).
Extract Handler: Read the content of the onclick attribute (e.g., submitForm(123)).
Rewrite HTML: Remove the onclick attribute and add the new ID.
Inject Script: Append an addEventListener block to the bottom of the script or a new file.
Code Example: Before Refactoring

HTML


<div class="user-card" onclick="showDetails(event, 42)">
  <span class="name">John Doe</span>
</div>


Code Example: After AST Transformation

HTML


<div class="user-card" id="user-card-42">
  <span class="name">John Doe</span>
</div>
<script>
  // Auto-generated binding
  document.getElementById('user-card-42').addEventListener('click', function(event) {
    showDetails(event, 42);
  });
</script>


This intermediate step is crucial. It decouples the HTML from the specific implementation of the function, allowing the function showDetails to eventually be moved into a module without touching the HTML again.22
4.3 Global Variable Consolidation
Implicit global variables (e.g., var isLoggedIn = true;) act as "ghost dependencies." Agents cannot easily track where these are modified.
The "AppState" Pattern:
We aggregate all global variables into a single global namespace object, window.AppState.
Before: var currentUser = 'Admin';
After: window.AppState.currentUser = 'Admin';
This simple refactor makes state dependencies explicit. An agent can now search for AppState to find every read/write operation on global data. It creates a "seam" where we can later inject a proper State Management system (discussed in Phase VI).23
5. Phase III: The ESM Transition (Module Infrastructure)
With events decoupled and state consolidated, we can transition the infrastructure to ES Modules (ESM). This moves the codebase from "Script Mode" (global scope, synchronous execution) to "Module Mode" (file scope, deferred execution, import/export support).24
5.1 The Entry Point Strategy
The transition begins by designating a main entry point. In index.html, we replace the classic script tag with a module tag:

HTML


<script type="module" src="./src/main.js"></script>


This single change alters the parsing rules of the browser:
Strict Mode: ESM enables 'use strict' automatically, preventing common legacy errors (e.g., accidental globals).25
Deferred Execution: Modules allow the HTML parser to finish constructing the DOM before scripts run, often eliminating the need for $(document).ready or DOMContentLoaded listeners.24
5.2 Analyzing the Module Dependence Graph (MDG)
To break the monolithic script.js into modules, we must understand the Module Dependence Graph. We categorize functions into three tiers 26:
Leaf Nodes (Utilities): Functions that rely only on their arguments and native APIs (e.g., formatDate, calculateTotal). These have zero dependencies on other application code.
Trunk Nodes (Business Logic): Functions that orchestrate Leaf Nodes and interact with the AppState (e.g., processCheckout, renderUserList).
Root Nodes (Initialization): The setup code that binds events and kicks off the application.
Refactoring Order of Operations:
Bottom-Up Extraction: Always extract Leaf Nodes first. Moving a Trunk Node before its dependencies are modularized creates complex import chains and circular dependencies.
Circular Dependency Management: Legacy code often has "A calls B, and B calls A." To resolve this, we introduce a third module "C" (shared state or event bus) that both A and B depend on, breaking the cycle.18
5.3 directory Structure for Agent Navigation
The file system structure is the "User Interface" for the Agent Engineer. A poorly organized file system wastes context tokens on ls commands and path resolution.
The Feature-First (Vertical) Directory Structure:
src/
├── features/ # Vertical Slices
│ ├── auth/ # Feature: Authentication
│ │ ├── components/ # UI Components specific to Auth
│ │ ├── services/ # API logic specific to Auth
│ │ └── index.js # Public API for this slice
│ ├── ticketing/ # Feature: Support Tickets
│ │ ├── ticket-list.js
│ │ ├── ticket-detail.js
│ │ └── ticketing.css
│ └── search/
├── shared/ # Truly shared code (use sparingly)
│ ├── infrastructure/ # Event Bus, HTTP Client
│ └── ui/ # Generic UI (Buttons, Modals)
└── main.js # Application Bootstrapper
This structure ensures that when an agent works on "Ticketing," it can request the content of src/features/ticketing and receive all relevant context (UI, Logic, Styles) without noise.1
6. Phase IV: Componentization via Native Web Components
The core of the Vertical Slice architecture is the Web Component. By converting UI sections into Custom Elements (e.g., <ticket-list>), we encapsulate the DOM structure and behavior, enforcing the boundaries of our vertical slices.28
6.1 Why Web Components?
For a vanilla JS refactor, Web Components are the logical choice over React or Vue:
No Build Step: They run natively in the browser. This aligns with the requirement to keep the "exact same UI" without introducing a compilation layer that might alter CSS specificity or script execution order.6
Standardization: They provide a standard lifecycle (connectedCallback, disconnectedCallback) that agents can rely on for setup and teardown logic.28
6.2 The "Light DOM" Strategy for Legacy CSS
A critical decision point is whether to use Shadow DOM. Shadow DOM provides style encapsulation (styles inside don't leak out; global styles don't bleed in).
The Conflict: The legacy monolith likely relies on a global stylesheet (e.g., Bootstrap, extensive style.css). Using Shadow DOM would block these global styles, breaking the UI.30
The Solution: Use Light DOM components. We extend HTMLElement but do not call attachShadow(). We render directly into this.innerHTML. This allows the component to benefit from logical encapsulation (JS) while still inheriting the global legacy CSS.
Component Pattern for Agent Engineers:

JavaScript


// src/features/ticketing/ticket-list.js
export class TicketList extends HTMLElement {
  constructor() {
    super();
    // Initialize internal state, do NOT access DOM here
  }

  connectedCallback() {
    // Lifecycle: Component added to DOM
    this.render();
    this.addEventListeners();
  }

  render() {
    // Light DOM rendering allows legacy CSS to apply
    this.innerHTML = `
      <div class="ticket-list-container">
        <table class="legacy-table-class">
          <thead>...</thead>
          <tbody id="ticket-rows"></tbody>
        </table>
      </div>
    `;
  }

  addEventListeners() {
    // Scoped event listening
    this.querySelector('table').addEventListener('click', (e) => {
      this.handleRowClick(e);
    });
  }

  handleRowClick(e) {
    // Business logic
  }
}
customElements.define('app-ticket-list', TicketList);


This pattern allows an agent to identify a section of index.html, wrap it in this class structure, and replace the original HTML with <app-ticket-list></app-ticket-list>.32
6.3 CSS Refactoring Strategy
While we rely on global CSS initially, we want to move toward modularity.
Extraction: Identify CSS rules specific to the slice.
Collocation: Move them to src/features/ticketing/ticketing.css.
Scoping: Adopt BEM (Block Element Modifier) naming conventions (e.g., .ticket-list__item) to simulate encapsulation without the Shadow DOM boundary.33
7. Phase V: State Management and Inter-Slice Communication
In a monolithic architecture, components (script functions) communicate by reading and writing to the DOM or global variables. In a modular architecture, we need a disciplined way for Vertical Slices to share data without becoming tightly coupled.
7.1 Decoupling with Pub/Sub (Publish-Subscribe)
To ensure that the "Search" slice doesn't need to import the "Ticket List" slice directly (which would recreate the monolith's spaghetti dependencies), we implement an Event Bus.
Mechanism: Components emit named events (ticket:created, user:logged-in) to a central bus. Other components subscribe to these events.
Benefit: The "Search" feature only needs to know that a search occurred, not who consumes the result. This makes the system extremely flexible and easy for agents to extend.23

7.2 The Reactive State Store (Single Source of Truth)
While Pub/Sub handles events, we need a persistent place to store shared data (e.g., the current list of tickets). We implement a lightweight, reactive store using JavaScript Proxy objects. This avoids the boilerplate of libraries like Redux while providing "magic" reactivity.37
Implementation Detail:
The Store object wraps the state data. When a property is modified, the Proxy intercepts the set operation and automatically emits a change event via the Event Bus.

JavaScript


// src/shared/store.js
const initialState = { tickets:, user: null };

export const store = new Proxy(initialState, {
  set(target, property, value) {
    target[property] = value;
    // Auto-notify subscribers
    EventBus.emit(`state:${property}`, value);
    return true;
  }
});


Components simply subscribe to state:tickets to react to changes. This gives the Agent Engineer a clear data flow: Action -> Update Store -> Proxy triggers Event -> UI Updates. This linearity reduces the reasoning required to debug state issues.37
8. Execution Protocols for Agent Engineers
This section translates the architectural strategy into specific operational protocols for Agent Engineers. These are the rules of engagement the agents must follow to execute the refactor successfully.
8.1 The Strangler Fig Execution Pattern
We do not rewrite the site in one go. We use the Strangler Fig Pattern, gradually migrating features while the legacy system continues to run alongside.4
Phase 1: The Skeleton
Agent creates the directory structure.
Agent sets up main.js and imports it in index.html.
index.html remains 99% legacy code.
Phase 2: The Slicing Loop (Iterative)
For each feature (e.g., "Footer"):
Identify: Agent locates the HTML for the footer and associated CSS/JS.
Snapshot: Agent runs VRT to capture the baseline of the footer.
Extract: Agent creates src/features/footer/footer-component.js and copies the logic/HTML there.
Replace: Agent replaces the legacy HTML block with <app-footer></app-footer> in index.html.
Verify: Agent runs VRT. If pixels differ, Agent iterates on CSS until a match is found.
Commit: Once green, the legacy code is deleted.
8.2 Prompting Strategies for Context Management
To prevent context overflow, human supervisors should prompt Agent Engineers using Context-Constrained Prompts.
Bad Prompt: "Refactor the ticket list." (Agent might read the whole repo).
Good Prompt: "Refactor the 'Ticket List' feature. The relevant legacy HTML is in the #ticket-table div of index.html. The legacy logic is in js/scripts.js lines 400-600. Create a new Vertical Slice in src/features/ticketing. Do not modify the Navigation or Footer."
By explicitly bounding the scope, we force the agent to focus its attention mechanism on the high-value tokens, improving code quality and reducing hallucinations.3
8.3 Governance and Linter Rules
We enforce architectural rules via static analysis to ensure agents don't regress into spaghetti code.
Rule 1: No Global Access. ESLint rule no-undef and no-global-assign (except for AppState during transition).
Rule 2: Import Boundaries. Use eslint-plugin-boundaries to prevent features from importing other features directly (must use Shared or Event Bus).41
Rule 3: File Size Limits. Enforce a hard limit of 300 lines per file. This forces agents to decompose complex logic into smaller helpers, keeping the codebase agent-friendly indefinitely.42
9. Risk Analysis and Mitigation
9.1 The "CSS Bleed" Risk
Since we are using Light DOM, global styles from the monolith will affect new components, and new component styles could affect the monolith.
Mitigation: Enforce BEM (Block-Element-Modifier) naming for all new component classes (e.g., .ticket-card__title). This pseudo-namespacing prevents collisions with legacy generic classes like .title or .card.34
9.2 Race Conditions in Module Loading
ES Modules load asynchronously. Legacy scripts often run synchronously. This can lead to race conditions where a module tries to attach to a DOM element that legacy scripts haven't initialized yet (or vice-versa).
Mitigation: The main.js bootstrapper must wait for DOMContentLoaded. Furthermore, new components should defensively check for the existence of data or DOM nodes in their connectedCallback and set up MutationObservers if they need to react to legacy DOM changes.39
9.3 SEO and Initial Render performance
Web Components that render via JavaScript (client-side) can have a delay before content appears (Flash of Unstyled Content - FOUC) or be slower for search engines to index compared to raw HTML.
Mitigation: For critical "above-the-fold" content, we can use Declarative Shadow DOM (if adopting Shadow DOM later) or keep the initial HTML structure in index.html and have the Web Component "hydrate" it (attach behavior to existing DOM) rather than replacing it entirely.29
10. Conclusion
The transformation of a monolithic support site into a modular, agent-optimized system is a complex but necessary evolution. By adopting Vertical Slice Architecture, we align the codebase structure with the cognitive constraints of Agent Engineers, enabling them to navigate, reason, and modify the system with high precision.
This Master Plan prioritizes Context Engineering—optimizing token density and locality of reference—over traditional aesthetic refactoring. Through the disciplined application of Visual Regression Testing, AST-based Code Decoupling, and Native Web Components, we ensure that the system not only preserves its exact original functionality but also becomes a robust platform for the future of AI-augmented software development.
The resulting architecture is standardized, resilient, and "vanilla"—free from the churn of build tools and frameworks, ready to be maintained by the next generation of silicon-based engineers.

  connectedCallback() {
    this.render();
    this.addListeners();

    // Auto-cleanup to prevent memory leaks
    this.unsubscribe.forEach(unsub => unsub());

   * Helper to bind events that are automatically cleaned up

    const el = this.querySelector(element);

      el.addEventListener(event, boundHandler);
      this.unsubscribe.push(() => el.removeEventListener(event, boundHandler));
    }
